## Project Overview

Oxtro API is a Go backend with a WordPress-inspired plugin system. It uses ConnectRPC (protobuf-based RPC over HTTP) instead of REST, GORM for database access, and a hook engine (actions/filters) that lets plugins extend core behavior without modifying core code.

## Common Commands

```bash
make run                    # Run server (Linux, uses gow for hot reload)
make test                   # Run all tests: go test -v ./...
go test -v ./path/to/pkg    # Run tests for a specific package
go test -v -run TestName ./path/to/pkg  # Run a single test

make gen-proto              # Generate Go code from core .proto files (oxtro-proto/)
make gen-proto-plugin       # Generate Go code from plugin .proto files
make gen-proto-all          # Generate all proto files

make migration-create name=<name>    # Create new migration files
make migration-up version=<N>        # Run N migrations up
make migration-down version=<N>      # Roll back N migrations
```

**Prerequisites:** `buf`, `protoc-gen-go`, `protoc-gen-connect-go`, `migrate` CLI, `mockery v2.45.0`

## Architecture

### Layered Structure (per feature)

Each feature follows a strict 5-layer pattern:

1. **Proto definition** (`oxtro-proto/<feature>/v1/<feature>.proto`) - RPC service and message definitions
2. **Generated code** (`gen/<feature>/v1/`) - Auto-generated by `buf generate`, never edit manually
3. **Domain interfaces** (`domain/domain_<feature>.go`) - Repository and Service interfaces with `//go:generate mockery` directives
4. **Repository** (`repository/repo_<feature>/`) - GORM database queries implementing domain repository interface
5. **Service** (`service/service_<feature>/`) - Business logic implementing domain service interface
6. **Handler** (`handler/handler_<feature>/`) - ConnectRPC handler that delegates to service, embeds `Unimplemented*Handler`
7. **Router** (`routers/router_<feature>.go`) - Wires handler into the HTTP mux
8. **Injector** (`injector/injector_<feature>.go`) - Manual dependency injection (repo -> service -> handler)

### Key Conventions

- **Module path:** `app` (import as `app/...`)
- **API protocol:** ConnectRPC (not REST). Handlers implement generated `*connect.Handler` interfaces. Errors use `connect.NewError(connect.Code*, err)`.
- **Auth:** JWT Bearer tokens via `middleware.NewAuthInterceptor`. Public endpoints are explicitly whitelisted. Authenticated context accessed via `middleware.PrincipalFromContext(ctx)`.
- **Setup gate:** `middleware.WithSetupGate` blocks all non-setup endpoints until initial setup is completed.
- **Mocks:** Generated in `domain/mocks/` using mockery. Regenerate with `go generate ./domain/...`
- **DTOs:** Used only for non-RPC features (setup). RPC features use protobuf messages directly as request/response types.
- **Constants:** Error constants live in `constant/` package, organized by feature.

### Plugin System (`plugin/` + `plugins/`)

The plugin system is modeled after WordPress:

- **Plugin interface** (`plugin.Plugin`): `Manifest()`, `OnInstall`, `OnActivate`, `OnDeactivate`, `OnUninstall`
- **Optional interfaces:** `RouteRegistrar`, `MigrationProvider`, `HookSubscriber`, `UIManifestProvider`
- **Hook engine** (`plugin.HookEngine`): `AddAction`/`DoAction` (fire-and-forget events), `AddFilter`/`ApplyFilters` (data transformation pipeline). Priority-ordered, plugin-scoped cleanup on deactivation.
- **Plugin routes** are auto-prefixed at `/plugins/{plugin_id}/`
- **Plugin lifecycle:** Register (compile-time in `main.go`) -> Install -> Activate -> Deactivate -> Uninstall
- **Plugin config:** Per-plugin key-value store via `PluginConfigStore` interface
- **UI Manifests:** Schema-driven UI metadata (navigation, views, actions) for host-rendered frontends

Plugins live in `plugins/` directory. See `plugins/sample_crm/` for the reference implementation.

### Protobuf / Code Generation

- Proto source files: `oxtro-proto/` (core) and `plugins/<name>/proto/` (per plugin)
- Workspace config: `buf.work.yaml` references both directories
- Generated Go + Connect code goes to `gen/` (core) or `plugins/<name>/gen/` (plugins)
- Each plugin can have its own `buf.gen.yaml` for independent code generation

### Middleware Stack (outer to inner)

`RequestLogger` -> `CORS` -> `SetupGate` -> `AuthInterceptor` (ConnectRPC interceptor, per-service)

### Database

- PostgreSQL via GORM (`config/db.go`)
- Migrations in `migrations/` using golang-migrate (raw SQL, sequential numbering)
- Plugin migrations handled separately via `MigrationProvider` interface
- Environment config via `.env` file (see `.env.example`)
